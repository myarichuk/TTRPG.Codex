# Flavor text: instructions for worker agents

Yes, this is a good job for Haiku. It is mechanical, templated, parallel and easy to check, and the
output is reviewed before it ships. The dispatcher (a Sonnet/Opus session) splits the work into
batches, gives each Haiku worker one batch plus the **Worker brief** below, and validates what
comes back. Workers never edit existing content files.

## What we are producing

The SRD pack (`content/systems/srd5e/packs/srd-5.2.1/`) is generated by `tools/Codex.ContentImport`
and carries rules text only. We add **original flavor** (short lore and visual description) in a
**separate overlay pack** so the SRD pack stays regenerable and its licence stays clean:

```
content/systems/srd5e/packs/codex-flavor/
  manifest.yaml                 written by the dispatcher, not by workers
  flavor/
    spell/spell-001.yaml        one file per batch
    monster/monster-001.yaml
    magic-item/magic-item-001.yaml
    class/class-001.yaml        classes, subclasses, species, backgrounds, feats and conditions
    ...                         get one file each (they are small)
```

A flavor file is a YAML list. One item per entry, keyed by the **id of the entry it decorates**:

```yaml
- id: fireball
  flavor: >-
    Old hedge-wizards say the first fireball was an accident: a bargain struck with a candle, and
    a candle that remembered every wick it had ever lit. Cast it and the air tastes of struck flint
    just before the world goes orange.
- id: owlbear
  flavor: >-
    ...
  habitat: Old forests and the ruins that forests swallow.
  imagePrompt: >-
    A hulking feathered bear with an owl's round face, mid-charge through ferns, dusk light.
```

Fields by type:

| Entry type | Required | Optional |
|---|---|---|
| `spell` | `flavor` | |
| `monster` | `flavor`, `imagePrompt` | `habitat`, `behavior` |
| `magic-item` | `flavor` | `imagePrompt` |
| `class`, `subclass`, `species`, `background`, `feat`, `condition` | `flavor` | `imagePrompt` (classes, species, backgrounds) |

`rules` entries get nothing. They are rules glossary text.

**Loader support:** the content loader merges each item's fields into the `properties` of the SRD entry
with the same type and id (see "Flavor" in `docs/CONTENT_PACKS.md`, which also explains why the lore is a
separate pack). The overlay pack must declare `dependencies: [srd-5.2.1]`.

## Worker brief (paste verbatim into each Haiku call)

> You write short, original fantasy flavor text for a tabletop RPG reference app. You are given a
> list of entry ids of one type, and the paths to their source YAML files. For each id:
>
> 1. Read the source file (`content/systems/srd5e/packs/srd-5.2.1/<type-folder>/<id>.yaml`) so the
>    text matches what the entry actually does. A fire spell smells of smoke; a necromancy spell
>    feels cold; a bat-like creature lives in caves.
> 2. Write the fields listed for that type, following the style rules below.
> 3. Write **one** output file at the path you were given, as a YAML list in the format above.
>    Output nothing but that file's content when asked to return text; no commentary.
>
> **Style rules**
> - **Original words only.** Never quote or paraphrase the entry's rules text, published
>   adventures, novels or any setting book. Do not restate mechanics (no dice, ranges, DCs).
> - **No trademarked or setting-specific names.** No named gods, planes, cities, nations, worlds,
>   characters or organisations from any published setting (so no Forgotten Realms, Greyhawk,
>   Eberron, Dragonlance, Ravenloft and the like). No wizard-name possessives such as
>   "Somebody's Whatever" unless the id already contains one. Use generic voices: "hedge-wizards",
>   "the old colleges", "river-folk", "a certain kind of priest".
> - **Do not name the game or its publisher.** No "D&D", "5e" or "Wizards of the Coast".
> - **Consistent with the entry.** Respect its school, damage type, creature type, alignment,
>   size and habitat. Do not contradict its rules text or invent new abilities.
> - **Length.** `flavor`: 2 to 3 sentences, 30 to 60 words (spells, items, feats, conditions);
>   40 to 80 words (monsters, classes, species, backgrounds). `habitat`/`behavior`: one sentence.
>   `imagePrompt`: one sentence of purely visual description, 15 to 35 words, no style or
>   artist names.
> - **Tone.** Evocative, concrete, a little wry; no second-person commands, no "you must",
>   no exclamation marks, no emoji, no markdown. Plain ASCII punctuation except for the
>   apostrophes and dashes already in the entry name.
> - **Variety.** Do not reuse an opening phrase within a batch. Avoid "Legend says" and
>   "It is said".
> - **Safety.** Violence is fine in the abstract (it is a monster manual); no gore for its own
>   sake, no real-world people, religions, slurs or sexual content.
>
> **YAML rules:** use the folded block form (`>-`) for every text value, indent two spaces, keep
> ids exactly as given (they are file names without `.yaml`), and include every id in the batch
> exactly once, in the order given.

## Dispatcher steps

1. **Build the batches** (~25 ids each; cheap enough that each worker finishes quickly):

   ```bash
   cd content/systems/srd5e/packs/srd-5.2.1
   ls spells | sed 's/\.yaml$//' | split -l 25 - /tmp/flavor-spell-
   ```

   Repeat for `monsters` (type `monster`), `magic-items` (type `magic-item`); for the small
   folders (`classes`, `subclasses`, `species`, `backgrounds`, `feats`, `conditions`) use one batch
   per folder.
   Approximate counts: 339 spells (14 batches), 341 monsters (14), 243 magic items (10), 69 others.
2. **Dispatch** one Haiku worker per batch (the `Agent` tool with `model: haiku`), a handful at a
   time, each with: the Worker brief, the entry type, the id list, and the output path
   `content/systems/srd5e/packs/codex-flavor/flavor/<type>/<type>-NN.yaml`. Give each worker its
   own output file; two workers never write the same path.
3. **Validate every file** before accepting it:
   - parses as YAML; every id exists in the SRD pack folder for that type; no duplicates; no
     missing ids from the batch;
   - word counts within the limits above;
   - none of the banned strings appear (case-insensitive): `D&D`, `Dungeons`, `Wizards of the Coast`,
     `Forgotten Realms`, `Faerun`, `Faerûn`, `Greyhawk`, `Eberron`, `Dragonlance`, `Ravenloft`,
     `Mordenkainen`, `Tasha`, `Bigby`, `Tenser`, `Mystra`, `Waterdeep`, `Baldur`, `Neverwinter`, `Drizzt`;
   - no digits followed by `d` and a number (dice), and no `DC `, `feet` or `ft.` (mechanics).
   Send failing batches back to a fresh worker with the failure list; do not hand-patch.
4. **Spot-check** a sample (about 5 percent, always the first file of each type) for tone,
   repetition and correctness against the rules text. Re-run any batch whose opening phrases repeat.
5. **Write `manifest.yaml`** for the overlay pack, matching the SRD pack's shape:
   `id: codex-flavor`, `systemId: srd5e`, `kind: world`, `priority: 1`,
   `dependencies: [srd-5.2.1]`, `authors: [TTRPG.Codex contributors]`, and a licence section
   stating the text is original work under the project's licence (decide which, see `LICENSE`).
6. **Commit** in a PR separate from the loader change so each can be reviewed alone.

## Order of work

Most-used first, so the app benefits early: `class`, `species`, `background`, `feat`,
`condition`, `subclass`; then `spell`; then `monster`; then `magic-item`.

## Explicitly out of scope

- Editing any file under `srd-5.2.1/`.
- Writing lore for `rules` entries or for equipment (plain gear has no flavor).
- Generating images. `imagePrompt` is only stored so art can be generated later (see the portrait
  work in the feature plan).
