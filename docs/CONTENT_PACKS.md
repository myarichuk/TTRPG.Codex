# Systems and content packs

Everything a game needs - attributes, the character sheet, classes, spells, monsters, places, lore -
is data. TTRPG.Codex loads it from **content roots** at startup:

- `plugins/` and `content/` next to the published executable (what a release ships), and
- the folders listed under `Codex:ContentDirectories` in `appsettings.json` (the repo's `content/`
  by default when running from source).

Inside a content root the layout is free-form; the loader looks for three kinds of thing anywhere
below it (skipping `bin/`, `obj/` and dot-folders):

| Thing | Marker | What it is |
|---|---|---|
| **System** | `system.yaml` | A game system: attributes, resources, sheet fields, content types, conditions, dice. |
| **Pack** | `manifest.yaml` (or legacy `manifest.json`), or a `.zip`/`.cdx` archive | Content for one system: rules, a setting, or homebrew. |
| **Compiled plugin** | `*.dll` directly in the root | An `ICodexSystemPlugin` for behaviour data can't express (custom dice, ECS systems). |

The shipped tree:

```
content/
  systems/srd5e/
    system.yaml                 Fifth Edition SRD (5.2.1) - the system definition
    packs/srd-5.2.1/            the SRD content, generated by tools/Codex.ContentImport
      manifest.yaml  LEGAL.md  classes/  spells/  monsters/  feats/  species/  ...
    packs/codex-flavor/         original lore and art prompts for the SRD entries (flavor/<type>/*.yaml)
  examples/
    simple-d6/                  a tiny homebrew system (system.yaml + packs/core)
    homebrew-world/             a setting pack for srd5e: lore, locations, NPCs
```

## system.yaml

```yaml
id: simple-d6                 # lower-case, stable; campaigns reference it
name: Simple d6               # shown in the UI
version: 1.0.0
compatibility: 5E compatible  # optional: the only product reference the UI shows
description: ...
license:                      # shown on the About page and under every entry
  name: CC-BY-4.0
  url: https://creativecommons.org/licenses/by/4.0/legalcode
  attribution: "This work includes material from ..."   # verbatim, if the licence requires one
  sourceUrl: https://...
  modified: true              # CC-BY: say so if you changed the material
  notices: [ "..." ]          # extra notices (upstream MIT, trademark disclaimers)

attributes:                   # per-actor scores; modifier: none | half-minus-five (the d20 rule)
  - { key: str, label: Strength, abbreviation: STR, default: 10, min: 1, max: 30, modifier: half-minus-five }

resources:                    # depletable pools; the primary one is what damage/healing target
  - { key: HP, label: Hit Points, maxKey: HP_Max, default: 10, isPrimary: true }
  - { key: TempHP, label: Temporary Hit Points }

actorFields:                  # the rest of the sheet; same field schema as content types
  - { key: level, label: Level, type: Number, defaultValue: 1 }
  - { key: class, label: Class, type: EntityReference, targetEntityType: class }   # picker from the Library

conditions: [Blinded, Charmed, ...]   # offered in the table's condition picker
dice: { initiative: 1d20, check: 1d20, initiativeBonus: initiative, initiativeTieBreak: dex }

vitals:                       # what the table does with hit points (all optional)
  temporaryResource: TempHP   # absorbs damage first; granted as "keep the higher"
  down: { condition: Unconscious, deadCondition: Dead, stableCondition: Stable, instantDeathAtMax: true, nonPlayersDieAtZero: true }
  deathSaves: { die: 1d20, successOn: 10, successesToStabilize: 3, failuresToDie: 3, criticalSuccess: 20, criticalFailure: 1 }
  damage: { types: [acid, fire, ...], resistancesField: resistances, immunitiesField: immunities, vulnerabilitiesField: vulnerabilities }
  exhaustion: { key: Exhaustion, maxLevel: 6 }          # a level counter, kept as a pool
  hitDice: { key: HitDice, levelField: level, classField: class, dieProperty: hitDie, creatureDiceProperty: hitDice, attribute: con }
  rests:
    - { name: Short Rest, spendHitDice: true }
    - { name: Long Rest, restores: [HP], clears: [TempHP], hitDiceRegain: half, exhaustionDelta: -1 }

entityTypes:                  # what packs for this system may contain
  - type: spell               # singular key; the Library groups by it
    label: Spell
    pluralLabel: Spells
    folder: spells            # pack folder (defaults to the type key)
    icon: flame
    summaryFields: [level, school]      # shown in list rows
    filterFields: [level, school]       # (reserved for facet filters)
    playerFacing: true                  # false hides the type from players' pickers (monsters)
    fields:
      - { key: level, label: Level, type: Number }
      - { key: school, label: School, type: Dropdown, options: [Abjuration, ...] }
      - { key: concentration, label: Concentration, type: Boolean }
      - { key: classes, label: Classes, type: TagList }
      - { key: features, label: Features, type: Collection }   # rows of {level?, name, description}
  - type: monster
    actorBlueprint: true                # entries double as creatures the DM can add to the cast
    hitPointsProperty: hitPoints        # which property seeds the primary resource
    attributeProperties: { strength: str, dexterity: dex }   # property -> attribute key
```

Field types: `Text`, `LongText`, `Number` (honours `min`/`max`), `Boolean`, `Dropdown` (`options`),
`TagList` (comma-separated), `EntityReference` (`targetEntityType`), `Collection` (rows), `ImagePicker`.

### Sheet rules (`sheetRules`)

What a character sheet may contain is data too, so a homebrew can be as strict or as loose as it
likes. Leave `sheetRules` out and anything goes. The SRD system uses every kind of rule:

```yaml
sheetRules:
  enforcement: strict          # strict: players can't save a sheet that breaks a rule (the DM always can)
                               # warn: show problems but allow saving; off: don't check.
                               # A campaign can override this under Settings > House rules.
  attributes:
    methods: [point-buy, standard-array]      # what players may pick; the DM also gets "manual"
    default: point-buy
    max: 20                                   # cap on base + bonuses
    pointBuy: { budget: 27, min: 8, max: 15, costs: { 8: 0, 9: 1, 10: 2, 11: 3, 12: 4, 13: 5, 14: 7, 15: 9 } }
    standardArray: [15, 14, 13, 12, 10, 8]
    bonuses:                                  # bonuses granted by a referenced entry
      label: Background bonuses
      fromField: background                   # the sheet field that references the entry
      property: abilityScores                 # that entry's list of eligible attributes (keys, abbreviations or labels)
      allocations: [[2, 1], [1, 1, 1]]        # allowed spreads, one bonus per distinct attribute
    increases:                                # score increases granted by picks (Ability Score Improvement)
      label: Ability score increases
      fromList: feats                         # the list whose picks can grant them
      property: abilityIncrease               # entry property: points to spread
      optionsProperty: abilityIncreaseOptions # entry property: attributes they may go to (none: any)
      capProperty: abilityIncreaseCap         # entry property: highest score they may reach (else `max`)
  derived:                                    # read-only, computed from numeric sheet fields
    - { key: proficiencyBonus, label: Proficiency Bonus, formula: "2 + (level - 1) / 4" }
    #  floor(), ceil(), max(), min() and mod(score) (the half-minus-five modifier) are available
  constraints:                                # on single-pick reference fields
    - field: subclass
      where:
        - { property: class, equalsField: class, message: "that subclass belongs to another class." }
    - field: originFeat
      where:
        - { property: category, equals: origin }
        - { property: id, equalsPropertyOfField: { field: background, property: feat } }
  lists:                                      # multi-pick lists shown under "Picks" on the sheet
    - key: spells
      label: Prepared spells
      targetEntityType: spell
      where:
        - { property: level, gte: 1 }
        - { property: classes, containsNameOfField: class }       # the spell's class list names the sheet's class
        - { property: level, lteLookup: { field: class, table: spellcasting, byField: classLevel, column: maxSpellLevel } }
      maxCount: { lookup: { field: class, table: spellcasting, byField: classLevel, column: preparedSpells } }
    - key: feats
      label: Feats
      targetEntityType: feat
      repeatableProperty: repeatable          # entries with repeatable: true can be picked more than once
  multiclass:                                 # levels split across classes
    key: multiclass                           # sheet key holding the other classes as "class-id:levels"
    classField: class                         # the first class; it gets the levels the others don't take
    levelField: level                         # the character level (proficiency, feat minimums)
    classLevelKey: classLevel                 # each class's own level, for lookups (byField: classLevel)
    prerequisitesProperty: multiclassPrerequisites   # class property: ["STR 13+", "DEX 13+, WIS 13+"], any one option
  slotPools:                                  # expendable slots, tracked during play
    - key: slots                              # resources slots_1, slots_1_Max, slots_2 ...
      label: Spell slots
      field: class
      byField: classLevel
      table: spellcasting
      column: slots                           # "4/3/2" = 4 level-1, 3 level-2, 2 level-3 slots
      excludeCasterTypes: [pact, none]        # filter classes by their casterType property
      recoversOn: [Long Rest]                 # a button per rest name at the table and on the sheet
      combine:                                # two or more contributing classes
        weights: { full: 1, half: 0.5 }       # class level x weight of its casterType...
        rounding: up                          # ...rounded per class (up, down or nearest)...
        table: ["2", "3", "4/2", "..."]       # ...summed, then row N of this table (caster level N)
    - key: pact
      label: Pact slots
      table: spellcasting
      column: slots                           # a count...
      slotLevelColumn: maxSpellLevel          # ...all of the level in this column
      includeCasterTypes: [pact]
      recoversOn: [Short Rest, Long Rest]
  hitPoints:                                  # maximum hit points from the classes' hit dice
    key: HP_Max                               # sheet key written (the primary resource's max key)
    currentKey: HP                            # follows the maximum: a larger one arrives as health
    attribute: con                            # modifier added per level
    dieProperty: hitDie                       # class property: "d10"
    modes: [average, rolled, manual]          # what a player may choose; default: average
    default: average
  armorClass:                                 # armor class from equipment, class features and bonuses
    key: armorClass
    unarmored: "10 + mod(dex)"                # formula used with no body armor (best of this and class formulas)
    bonusLists: [feats]                       # picks here may add armorClassBonus (a fighting style)
  inventory:                                  # what a character carries; stored as "item-id|qty:2,equipped:1"
    key: inventory
    label: Equipment
    types: [equipment, magic-item]
```

**Hit points.** Levels are counted first class first, then the others in order. The first level takes the
full hit die; every later level takes the die's average (`die / 2 + 1`) or, in `rolled` mode, the roll the
player entered (clamped to the die; levels without a roll use the average). Each level adds the
`attribute` modifier, never dropping below 1. Because the modifier comes from the final score, raising
Constitution raises every level's gain. The maximum is written to `key` while the sheet's `hpMode` is
`average` or `rolled`; a sheet without `hpMode` (an older character, a creature seeded from a stat block)
is manual and keeps whatever number it has. New characters start in the default mode. When the maximum
grows, current hit points grow with it; when it shrinks they are clamped.

**Armor class.** With a body armor equipped (an item whose `armorBase` is a number): `armorBase` plus the
Dexterity modifier, limited by `armorDexCap` (absent: no limit; 0: Dexterity does not count, in either
direction). With none: the highest of the `unarmored` formula and every class's `unarmoredDefense` formula
(a class whose `unarmoredDefenseShield` is false loses its formula while a shield is carried). Then it
adds `armorClassBonus` of every equipped item (a shield is an item with `armorType: shield` and a bonus),
of picks in `bonusLists` (skipped when `armorClassRequiresArmor` is true and no body armor is worn), and
the sheet's `armorClassMisc` number. It is written to `key` while the sheet's `acMode` is `auto`; without
that key the sheet is manual.

**Inventory.** Items may come from any of `types` (pack and homebrew entries alike). At most one body
armor and one shield can be equipped at a time.

The SRD importer fills the typed item and class properties (`armorType`, `armorBase`, `armorDexCap`,
`armorClassBonus`, `unarmoredDefense`, `unarmoredDefenseShield`, `armorClassRequiresArmor`) from the source
data, and homebrew armor sets them in the entry editor.

Conditions compare a property of the candidate entry (`level`, `classes`, `category`, or `id`,
`name`, `tags`) with a constant (`equals`, `in`, `gte`, `lte`), a sheet field (`equalsField`,
`lteField`, `gteField`), the entry another field references (`containsNameOfField`,
`equalsPropertyOfField`) or a value looked up in that entry's row table (`lteLookup`). A lookup
takes the row whose `level` (or `rowKey`) is the highest not above the sheet's `byField`. A
`maxCount` that looks up a table the chosen entry doesn't have is zero (a fighter's spells); with
nothing chosen yet it is unlimited.

Base scores live in the sheet as `base_<key>` and bonuses as `bonus_<key>`; the engine writes the
total (base + bonus + increases) into `<key>`, which is what the live table and the ECS use. List
picks are stored as lists of entry ids under the list's key; a pick that raises scores carries the
player's choice after a bar: `ability-score-improvement|str:1,dex:1`.

With `multiclass`, lists and slot pools are evaluated once per class, with the class field set to
that class and `classLevel` to its levels: an entry is allowed when any one class allows it, and
table-driven limits are added up (a wizard 3 / cleric 2 prepares both classes' spells, each up to its
own highest spell level). A class's prerequisites are checked against final scores, for every class
including the first once there is more than one.

Slot pools become resources: `slots_3` is the remaining level-3 slots and `slots_3_Max` the maximum.
The sheet keeps the maximum in step with the classes (a new slot arrives available, a lost slot level
disappears); the live table spends and regains them and refills them on the named rests.

Validation runs at load. A broken `system.yaml` is reported on the About page under "Content
warnings" and the system is skipped; nothing else stops loading.

## manifest.yaml

```yaml
id: srd-5.2.1                 # unique across all packs
name: System Reference Document 5.2.1
version: 5.2.1
systemId: srd5e               # the system this pack belongs to
kind: rules                   # rules | world | homebrew (informational)
priority: 0                   # higher wins when two packs define the same entry id
dependencies: [other-pack]    # loaded first, so `inherits` can resolve
description: ...
authors: [ ... ]
license: { ...as above... }
```

## Entries

Each file under a type folder holds one entry or a list of entries:

```yaml
- id: fireball                # stable within the type
  name: Fireball
  description: |              # Markdown subset: **bold**, *italic*, "- " bullets, | tables |, ### headings
    *Level 3 Evocation*
    ...
  tags: [evocation, level-3]
  inherits: fire-bolt         # optional: id (same type), type:id, or system:type:id
  properties:                 # the type's fields; numbers and booleans are typed automatically
    level: 3
    school: Evocation
    classes: [Sorcerer, Wizard]
```

Three legacy folders keep their older, richer shapes: `abilities/` (executable TRCE abilities),
`actors/` (NPC blueprints with `resources` and `properties`), `locations/` (places with
`parentId` and `connections`). Setting packs use `actors/` and `locations/` for their people and
places, and a `lore` entity type for everything else.

## Flavor: lore and art prompts

Every entry can carry a little lore. Four property keys are understood in every system, whatever its
entity types:

| Key | What it is | Shown as |
|---|---|---|
| `flavor` | 2-3 sentences of lore | a quote above the rules text |
| `habitat`, `behavior` | one sentence each, mostly for creatures | ordinary labelled rows |
| `imagePrompt` | one visual sentence, for generating art | not shown; kept for the art tools |

There are three ways to give an entry flavor.

**Inline.** Put the keys in the entry's `properties`, in a pack file or in the homebrew editor. Every
entry type's editor in the Library has a *Lore* group with these fields (creature types also get habitat
and behavior) unless the system declares a field with the same key itself, in which case the system's
wins. This is how a table's own monster, magic sword or spell gets flavor.

**As an overlay on someone else's entries.** A pack can add lore to entries that *other* packs define,
without copying them. Put YAML lists under `flavor/<type>/` (the type key, such as `spell` or
`magic-item`) and make the pack depend on the one that defines the entries:

```yaml
# flavor/spell/spell-001.yaml
- id: fireball                # the entry's id in its own pack
  flavor: >-
    ...
- id: owlbear
  flavor: ...
  habitat: Old forests.
  imagePrompt: >-
    ...
```

The loader merges each item into the entry of that type and id. Only the four keys above and the
properties the entity type declares are accepted: flavor can add lore but never change a rule or the
entry's rules text. An id no loaded pack defines is logged, but its flavor is remembered: a campaign's
homebrew entry with that type and id picks it up wherever the entry has no lore of its own (what the
entry says itself always wins).

**Both together.** An entry's own keys win over an overlay for homebrew; for pack entries an overlay
fills in or replaces the keys it names.

### Why the SRD's lore is a separate pack that is merged

`srd-5.2.1` is a generated, CC-BY-4.0 transcription of the System Reference Document. Its manifest says
"no rules were changed", every entry shows the SRD's attribution, and it can be regenerated from the
source at any time. The lore is our own writing under a different licence (MIT), so it does not belong
inside that pack: written into those files it would be shown under the SRD's attribution as if Wizards of
the Coast had written it, and the next regeneration would erase it. So the lore ships as its own pack,
`codex-flavor`, and the loader merges it into the SRD's entries when the app starts. The reader sees one
entry; the footer credits the rules to the SRD and the lore to the flavor pack and its licence
(`flavorSource` on the entry names the pack). Anyone can replace our lore with their own tone, or drop
it, by changing which flavor pack they ship, without touching the SRD.

Flavor is merged into the entries themselves at load, so switching the flavor pack off for one campaign
does not hide it; and as with all packs, a new flavor pack is picked up at the next start.
`FLAVOR_TEXT_INSTRUCTIONS.md` describes how the shipped text was written and checked.

## Homebrew without files

A DM creates homebrew in the campaign's **Library** section. Entries use the same field schema as
the system's content types, are searchable alongside pack content, can be hidden from players while
drafting, travel with the campaign export, and can be exported as a pack (zip) with **Export
homebrew pack** - drop the zip into a content root to share it with another server.

## Importing the SRD

The SRD pack is generated, not hand-written:

```bash
dotnet run --project tools/Codex.ContentImport -- srd5e --download --source /tmp/srd-json --out content/systems/srd5e/packs/srd-5.2.1
```

`--download` fetches the 5e-bits JSON transcription from a pinned commit (see
`tools/Codex.ContentImport/SrdDownloader.cs`). The manifest it writes carries the verbatim SRD 5.2.1
attribution statement, the modification notice CC-BY-4.0 requires, and the 5e-bits MIT notice.
`tests/Codex.Tests/SrdPackSmokeTests.cs` checks the generated pack against the document's counts.
